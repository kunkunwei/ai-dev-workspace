# 流程：求职投递闭环（JD 评估 → 简历定制 → 表单填写 → 台账看板）

> 本文件是**通用化规程**：所有路径均为相对路径，不含任何个人信息、雇主信息或具体数字。
> 把它放到你的求职目录下，按 `examples/` 的骨架建好 `data/` 即可跑。

**适用范围**：`<求职目录>/` 下的所有求职相关操作。
**原则**：数字改前回源文件核（`证据索引.md`）；不自动提交表单。

---

## 两个事实源（改之前先读）

| 环节 | 唯一事实源 | 谁写 |
|---|---|---|
| **结构化简历** | `<求职目录>/data/profile.yaml` | 用户 + AI |
| **投递状态与进度** | **投递看板**（在线页 + 私有仓 `data.json`） | 用户（面板操作）；AI 读，必要时写回 |

> ⚠️ `data/applications.yaml` **不是状态事实源**（里面 `stage` 是录入时的快照）。
> 它只作**补充索引**：记录每个岗位对应的 `jd_file`（JD 存档）、`tailor_file`（简历定制记录）、
> `match`（W1 匹配度）——这三项面板的数据模型里没有。

## 其它参照（只读或按需）

| 文件 | 内容 | 谁写 |
|---|---|---|
| `<求职目录>/证据索引.md` | **能说什么 / 不能说什么**（数字表 / 技能表 / 边界表 / 必答追问表） | 只读，是评估的判据 |
| `<求职目录>/resume/*.md` + 构建脚本 | 排版流水线（Markdown → 定页数 PDF） | AI 按 W2 改 |
| `<求职目录>/jd/<日期>-<公司>-<岗位>.md` | JD 原文 + 评估结论 | AI 建 |
| `<求职目录>/tailor/<日期>-<公司>-<岗位>.md` | 每岗改动记录（原句→新句→依据） | AI 建 |

**红线**：`profile.yaml` 的 `boundaries` 一节列了不能写进简历的话。AI 改简历后必须自检这一节，命中即回退。

## W1 · 投递前评估

**触发语**：「评估这个岗位：<粘 JD 原文>」

1. 建 `jd/<YYYY-MM>-<公司>-<岗位>.md`：
   - 头部元信息（公司 / 岗位 / 地点 / 来源 / 录入日期 / 台账条目 id / 简历版本）
   - JD 原文（职责 + 任职要求 + 加分项，**原样保留，不要改写**）
   - `## 投递前评估` 三张表 + 结论
2. 读 `data/profile.yaml` 与 `证据索引.md`
3. 逐条比对 JD 的**硬性要求**与**加分项**，输出：
   - **命中**表：JD 要求 → 对应经历 → 证据锚点（文件:行号）
   - **缺口**表：JD 要求 → 有没有 → 能否短期补 → 补课材料在哪
   - **红线**表：JD 要求里命中 `boundaries` 的条目（写了就是硬伤）
4. 给结论：**匹配度 高/中/低** + 投/不投 + 若投则简历要动哪几条
5. 在 `data/applications.yaml` 追加条目，`stage: 待投递`，填 `jd_file` / `match` / `next_action`
6. 更新 `data/applications.yaml` 的 `updated` 字段

**纪律**：`match` 只能由这张表推出来，不要凭感觉给「高」。命中率低就照实写「低」。

---

## W2 · 简历定制 + 导出

**触发语**：「按这个 JD 改简历，出 <名字> 版」

1. 选基线：`resume/` 下能力结构最接近的那份
2. 允许改：核心能力条目的**取舍与排序**、项目/竞赛的**取舍与措辞**、量化数字的**取舍**
3. **不允许改**：数字本身。要改数必须回 `证据索引.md` 数字表找到源文件（★ 一手文件优先），确认后再改
4. 建 `tailor/<日期>-<公司>-<岗位>.md`，逐条记录：`原句 → 新句 → 依据（哪条 JD 要求 / 哪条证据）`
5. 构建并**验证页数符合目标**；超页就按 `tailor/` 记录的手法继续压缩
6. 构建后**搜一遍红线词**：`开发了.*驱动` / `调试经验`（配仅使用的协议）/ `寄存器级` 等（以 `boundaries` 为准）
7. 在 `data/applications.yaml`（补充索引）里补上 `resume` / `tailor_file` 字段

---

## W3 · 投递后更新进度

**触发语**：「XX 公司笔试通知了，11 月 3 号」/「刷一下看板」

### 日常是你在面板上操作（推荐）

打开面板在线地址（`https://`，**不要用 `file://`**，会丢数据也丢同步配置）：

- **投完一家** → 「添加投递」（公司速查会提示已投过该公司的哪些岗位，防重复）
- **收到通知** → 改状态，或看板上直接拖拽
- 「下一步安排」填笔试/面试时间 → 首页临近自动标红
- 每次改动自动 commit 到私有仓，多端同步，误删可从仓库历史恢复

### AI 侧怎么做

1. **读**：从私有仓的 `data.json` 读状态（含 `records` / `companyFlags` / `view` / `savedAt`）
2. **需要时写回**：AI 替用户新增/修改记录 → 改 `data.json` 并 commit → 用户刷新面板就看到
   - ⚠️ **`savedAt` 比较规则**：面板只在「远端 `savedAt` > 本地 `savedAt`」时采用远端。
     所以写回时必须把 `savedAt` 设成**比面板本地更新**的值（用当前毫秒时间戳），否则面板会忽略
   - ⚠️ **`data.json` 是文件内容本身**（原始 JSON），不是 base64。
     GitHub Contents API 会自己套 base64；如果用 git push 直接写文件，写的必须是原始 JSON。
     **这一条踩过坑：写 base64 会导致面板拉取时 `JSON.parse` 抛错并被静默吞掉**
3. `data/applications.yaml` 只在需要补 `jd_file` / `tailor_file` / `match` 时更新，**不要**在那里改 `stage`

**关于「自动获取进度」**：仍是**半自动**——把笔试/面试/拒信邮件正文粘给 AI，AI 解析后更新（或提醒你改）。**不做 IMAP 自动抓取**，理由见设计文档「明确不做」节。

---

## 禁止

- 不用自动投递脚本（招聘平台自动投递违反用户协议，有封号风险；且渠道是公司官网）
- 不自动提交网申表单（填表扩展只填值，提交永远人工）
- 不把简历正文复制进 `profile.yaml`（长段落用 `work_description.source` 指向外部文件）
- 含个人信息（手机号 / 邮箱 / 生日）的 `data/profile.yaml` **不进公开仓库**

## 验证

- W1 产出：`jd/` 有文件、`applications.yaml` 有对应条目、`match` 有依据
- W2 产出：`tailor/` 有改动记录、PDF 页数达标、红线词搜索无命中、数字能指到源文件
- W3 产出：`applications.yaml` 的 `events` 追加了、看板刷新、已提交推云端
