# 01 · 求职投递闭环：四段结构 + 数据流 + 架构取舍

> 目标：把「JD 评估 → 简历定制 → 在线表单填写 → 投递进度看板」串成一个闭环，
> 和本地 AI 工作台及其 AI 搭在一起。
> 原则：**尽量不重复造轮子**。能用现成工具的用现成工具，能交给 AI 的不写代码。

---

## 一、先盘点已有的（别重造）

| 资产 | 作用 |
|---|---|
| 简历排版流水线（Markdown + 构建脚本 + 样式） | Markdown → 定页数 PDF（headless Chrome） |
| 在线简历文本 / 工作描述（多长度版本） | 官网字段的粘贴源 |
| **证据索引** | **能说什么 / 不能说什么**（数字表 / 技能表 / 边界表 / 必答追问表） |
| 面试资料 | 追问应答 |
| AI 工作台（facts / procedures / known-issues / decisions + git） | 事实源纪律 + 云端同步 |
| AI 编码工具 | 执行层 |

**最关键的资产是「证据索引」**——它让 AI 做的评估和改简历都有**边界**，通用求职工具没有这张表。
所以 JD 评估和简历定制不该外包给开源项目，该交给工作台的 AI。

---

## 二、闭环四段：每段用什么

```
① JD 录入与评估        ② 简历定制              ③ 在线表单填写           ④ 台账与看板
   ↓                     ↓                       ↓                       ↓
 jd/<岗位>.md      tailor/<岗位>.md        填表扩展                 applications.yaml
 AI 对照证据索引     resume/<岗位>.md        + profile.yaml          → 看板 / 面板
 输出匹配/缺口/风险   build → PDF            → 表单模板 JSON            AI 读邮件更新状态
```

| 段 | 现成工具 | 要补的 | 代码量 |
|---|---|---|---|
| ① 评估 | AI agent（不用工具） | JD 录入模板 + 评估规程 | 0 |
| ② 定制 | 已有排版流水线 | 每岗改动记录（可追溯）+ 单一事实源 | 0 |
| ③ 填表 | 填表扩展 | `profile.yaml` → 扩展模板 JSON 的转换脚本 | 少量 |
| ④ 看板 | 现成单页面板 / 不引入新工具 | `applications.yaml` + 状态维护 | 少量 |

**为什么不部署独立服务型应用**：它们功能对得上，但都是「需要自己搭服务的独立应用」，
会变成**第二套事实源**。工作台有明确的「事实源文件化 / 单一云端源 / 改完就提交推云端」纪律，
再引入一套本地服务，数据就要手工同步两遍——这是净负担。用 git 里的 YAML + 现成面板，
反而能和现有纪律长在一起。

## 三、单一事实源（这是整个闭环的承重墙）

同一个信息散在多份文件里（各岗位简历、在线简历文本、工作描述、证据索引…），
改一处要手工同步其他几处——**这是求职季最痛的 point，也是闭环必须先解决的点**。

### 3.1 `data/profile.yaml`

结构化简历，**唯一事实源**。其他所有产物都从它派生。骨架见
[`../examples/profile.example.yaml`](../examples/profile.example.yaml)。

```yaml
version: 1
updated: <YYYY-MM-DD>

basic:
  name: <姓名>
  phone: <手机号>
  email: <邮箱>
  birthday: <YYYY.M>        # 精确到月即可
  political: <政治面貌>
  degree: <学历>
  school: <学校>
  major: <专业>
  period: <YYYY.MM~YYYY.MM>
  graduate_year: <YYYY>
  photo: resume/photo.png
  courses: [...]

job_intent:
  target_roles: [<目标岗位>]
  cities: [<意向城市>]
  available_from: <YYYY.MM>

# 核心能力：一条一句话，带证据锚点和风险等级
skills:
  - title: <技能名>
    text: <一句话能力描述>
    risk: low|mid|high   # low=有源文件支撑 / mid=只有学校项目 / high=不能讲
    evidence: <证据锚点 文件:行号>

education: [...]
internships: [...]
projects: [...]
competitions: [...]

# ★ 红线：AI 做评估和改简历时必须自检的「不能写」
boundaries:
  - <不能写进简历的表述，例如「X 方向只有使用经验，无调试经验」>
```

> `boundaries` 这一节是**防幻觉用的**。AI 改简历时如果写出红线内的话，你能一眼看出来。

### 3.2 `data/applications.yaml`

投递台账。骨架见 [`../examples/applications.example.yaml`](../examples/applications.example.yaml)。
看板、统计、跟进提醒全部从它生成（或由它作为「补充索引」喂给现成面板）。

```yaml
version: 1
updated: <YYYY-MM-DD>
stages: [待投递, 已投, 笔试, 一面, 二面, 三面, HR面, Offer, 已挂, 放弃]

applications:
  - id: <YYYY-MM>-<公司>-<岗位>
    company: <公司名>
    position: <岗位名>
    channel: 官网
    city: <城市>
    match: 高               # 高 / 中 / 低（由 ① 段评估得出）
    stage: 待投递
    next_action: <下一步>
    jd_file: jd/<岗位>.md
    tailor_file: tailor/<岗位>.md
    resume: resume/<岗位>.md
    events:
      - {date: <YYYY-MM-DD>, stage: 待投递, note: <事件>}
```

## 四、目录结构（本 case study 的通用版）

```
<你的求职目录>/
├── data/
│   ├── profile.yaml            # 【唯一事实源】结构化简历（含个人信息，不进公开仓）
│   └── applications.yaml       # 【唯一事实源】投递台账
├── jd/                         # 每岗一份 JD 原文 + 评估结论
│   └── <YYYY-MM>-<公司>-<岗位>.md
├── tailor/                     # 每岗一份定制记录（改了哪几句、为什么）
│   └── <YYYY-MM>-<公司>-<岗位>.md
├── tools/                      # 可选，只有一个脚本且非必需
│   └── to_formfill.py          # profile.yaml → 填表扩展模板 JSON
├── resume/                     # 排版流水线（不改）
└── 证据索引.md                  # 能说什么 / 不能说什么（防幻觉判据）
```

## 五、三条工作流（AI 可执行）

### W1 · 投递前评估

**触发**：「评估这个岗位：<粘 JD>」

1. 建 `jd/<日期>-<公司>-<岗位>.md`，把 JD 原文和来源链接存进去
2. 读 `data/profile.yaml` + `证据索引.md`
3. 逐条比对 JD 的**硬性要求**，输出三张表：
   - **命中**：JD 要求 → 对应经历 → 证据锚点
   - **缺口**：JD 要求 → 有没有 → 能不能短期补
   - **红线**：JD 要求里有、但 `boundaries` 里明令不能讲的
4. 给结论：**匹配度 高/中/低** + 投/不投 + 如果投，简历要动哪几条
5. 写 `tailor/<岗位>.md`，并在 `applications.yaml` 加一条 `stage: 待投递`

### W2 · 简历定制 + 导出

**触发**：「按这个 JD 改简历，出 <岗位> 版」

1. 以能力结构最接近的现存简历为基线
2. **只改**：核心能力排序、项目/实习的取舍与措辞、量化数字的取舍
3. **不改**：数字本身（改数必须回源文件核，见证据索引表 A）
4. 每处改动写进 `tailor/<岗位>.md`：`原句 → 新句 → 依据（哪条 JD 要求 / 哪条证据）`
5. 构建 PDF 并**验证页数符合目标**（超页就按 `tailor/` 记录继续压缩）
6. 同步更新 `applications.yaml` 的 `resume` 字段

### W3 · 投递后更新（含看板刷新）

**触发**：「XX 公司笔试通知了，11 月 3 号」/「刷一下看板」

1. 更新 `applications.yaml` 里对应条目的 `stage` / `next_action` / `next_due`，并往 `events` 追加一条
2. 刷新看板（零脚本或现成面板）
3. 提交推云端（工作台纪律）

**关于「自动获取进度」**：真实可达的是**半自动**——你把笔试/面试/拒信邮件的正文粘给 AI，
AI 解析后更新 YAML。不建议做 IMAP 自动抓取（要存邮箱授权、规则维护成本高、收益半年就归零）。

## 六、和现有工作台的接口

1. **写成一条 procedure**：`procedures/job-application-loop.md`
   —— 任何 AI 进来读一次就知道怎么做
2. **`AGENTS.md` 加一行**，指向这条 procedure 和 `data/`
3. **云端同步**：`data/` 进 git（跟工作台一起推远端）。
   ⚠️ **`profile.yaml` 含手机号、邮箱、生日**——要么把该仓库设为 **private**，
   要么把 `data/profile.yaml` 加进 `.gitignore` 并在本地维护。
   **别把含个人信息的 YAML 推进公开仓库。**

## 七、分期落地

### 第一期：零代码就能跑

- [x] 建 `data/profile.yaml`、`data/applications.yaml`
- [x] 建 `jd/`、`tailor/` 目录
- [x] 写 `procedures/job-application-loop.md`
- [ ] 装填表扩展，先**粘贴简历原文**的方式跑通（这一步不需要转换脚本）

### 第二期：改用现成工具（不写脚本）

- **在线表单填写**：填表扩展自带「AI 导入」（粘贴文本 → 模型做字段映射 → 本地确定性填值）。
  转换脚本是可选的**确定性替代**（不调模型、不会幻觉），不用也不影响闭环。
- **看板**：用现成单页面板（单个 HTML 双击就用，零依赖，可选同步到私有仓）；
  或让 AI 直接读 `applications.yaml` 出 Markdown 看板（零代码、零依赖）。

### 第三期：可选增强

- [ ] 每岗的 `tailor/` 记录汇总成「哪个说法最常被追问」的反馈表，反哺 `证据索引.md`
- [ ] 若采用外部看板，把 `applications.yaml` 作为**唯一录入源**，导出 CSV 喂过去，避免双写

## 八、明确不做

| 不做 | 理由 |
|---|---|
| **自动投递脚本** | 只覆盖招聘平台，而渠道是公司官网；且违反平台协议有封号风险 |
| **自己写填表扩展** | 已有现成扩展做「AI 只做字段映射、本地确定性填值、不自动提交」，重造没有增量 |
| **部署独立服务型应用** | 会变成第二套事实源，和「单一云端源」纪律冲突 |
| **IMAP 自动抓邮件** | 授权 + 规则维护成本高，收益半年归零。半自动（粘邮件正文给 AI）足够 |
| **把简历正文写进代码** | 简历文本留在 Markdown，`profile.yaml` 只存**结构化字段**，不复制长段落 |

## 九、这套设计能给你什么

| 你想要 | 怎么实现 |
|---|---|
| 快速评估岗位投递可行性 | W1：AI 对照证据索引输出 命中/缺口/红线 三张表 |
| 快速改简历提高匹配度 | W2：单一事实源 + 每岗改动可追溯（原句→新句→依据） |
| 一键填写在线简历 | 第三段：`profile.yaml` → 填表扩展模板 JSON → 侧边栏点填充 |
| 自动获取进度更新面板 | W3：粘邮件给 AI → 更新 `applications.yaml` → 刷新看板 |
| 不重复造轮子 | 只写少量脚本，其余全用现成工具 + AI |
