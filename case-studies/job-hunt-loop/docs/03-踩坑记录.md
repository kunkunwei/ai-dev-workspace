# 03 · 踩坑记录：6 条真实工程坑

> 这些坑都是真实踩过的，纯技术、可复用，与具体行业无关。
> 场景：用「单页面板 + GitHub 私有仓」做投递进度看板，AI 侧读写私有仓的 `data.json`；
> 以及用 Markdown + 共用样式 + headless 浏览器导出定页数的 PDF 简历。

---

## 坑 1：`file://` 打开的单页应用，localStorage 会丢

**现象**：「数据和应用同步配置一起消失」。双击 HTML 用本地文件协议打开时，
浏览器对 `file://` origin 的 `localStorage` 不保证持久，换个路径、清一次临时数据、
或浏览器升级都可能清空。于是**数据和「连到私有仓的同步配置」一起没了**。

**正解**：部署到 `https://`（如 GitHub Pages）用**稳定 origin**。
`https://<用户名>.github.io/<仓名>/` 的 origin 是稳定的，`localStorage` 按 origin 隔离且持久。
以后只用这个在线地址，别再用双击 `file://` 打开。

> 关联坑 4：本地文件协议还会让「多端同步」无从谈起——每台机器的 localStorage 是各管各的，
> 一换设备数据就「丢」了。

## 坑 2：往 GitHub Contents API 预置文件时，文件内容是原始 JSON，不是 base64

**现象**：面板从私有仓拉 `data.json`，应用侧代码 `JSON.parse(atob(content))` 直接抛错，
被 `try/catch` **静默吞掉**。表现是「同步配置正常，但数据不出现」——没有报错，极难排查。

**根因**：GitHub Contents API 的「获取内容」返回的是 base64，但**「写入内容」接口收的是
原始内容字节**，GitHub 自己会套 base64 存进去。如果预置时把内容先 base64 再写入，
就存了双重 base64。面板拉回来后 `atob(content)` 解出的不是 JSON，于是 `JSON.parse` 抛错。

**判别法**：写完后**从远端 clone 回来复核一次**，能解码成可读 JSON 才算对。

**正解**：

- 用 GitHub Contents API 写入 → 传**原始 JSON 字符串**（`"content": <原始 JSON>`）
- 用 `git push` 直接写文件 → 写的也必须是**原始 JSON**
- 两种方式殊途同归：文件里存的是原始 JSON，不是 base64

> **补记（后来的实测）**：上面这条被写进操作说明时漏了推导过程，导致同一份说明的**另一节**
> 仍然写着「文件内容是 `base64(JSON)`」——那是**初版种子**的形态（手工预置、经 API 写入）。
> 面板自己写出来的一直是原始 JSON。同一件事在两个地方各说各话，比写错更难查。
> 教训：**把形态和「写入路径」绑在一起写**（见下表），而不是只写一个结论。

| 写入路径 | 磁盘上的形态 | 谁负责套 base64 |
|---|---|---|
| 浏览器面板直接提交 | **原始 JSON** | 不套 |
| GitHub Contents API | `base64` | **API 自动套**，传进去的必须是原始 JSON |
| `git push` 直接写文件 | **原始 JSON** | 不套 |

## 坑 3：同步的 `savedAt`「远端更新才采用」规则

**背景**：单页面板的云同步逻辑是**「远端 `savedAt` 比本地新就采用」**（单行判断，无冲突合并）。

**现象**：AI 替用户新增记录，写回私有仓后用户刷新面板，**新记录不出现**。

**根因**：写回的 `data.json` 里 `savedAt` 没设，或设成了比面板本地值更旧的值。
面板本地已有一次保存记录（本地 `savedAt` 较新），于是按规则**忽略了远端**。

**正解**：从外部写回数据时，**必须把 `savedAt` 设成大于对端当前值**（例如取当前毫秒时间戳）。
这样面板一刷新就会采用远端。

**更稳的姿势**：预置云端数据时也利用这条规则——把 `savedAt` 设成一个**远大于空白本地状态**的值，
面板首次配置好同步、一刷新就会自动把数据拉下来，**连「导入」按钮都不用点**。

## 坑 4：last-write-wins 竞争

**现象**：AI 从外部改数据（写回私有仓），应用正开着并保存，会把 AI 的改动**覆盖掉**。

**根因**：这套方案没有冲突合并，是 **last-write-wins**。谁最后保存谁赢。
应用开着时它本地有一份较新的内存态，AI 从远端读到的是旧数据，AI 写回后，应用紧接着保存，
就用应用本地（旧 + 用户最新操作）覆盖了 AI 的远端改动。

**正解（流程纪律，而非代码）**：

1. **从外部改数据前，必须先拉取最新版**——从私有仓 `git pull` 或 API 取当前 `data.json`，基于最新版改
2. **改的时候提醒应用端暂停保存**（或明确告知「正在外部修改，先别动面板」）
3. 写回后让用户**刷新面板**再继续操作，避免面板用内存态反写

**本质**：last-write-wins 不是 bug，是取舍。要省掉「拉取-改-提醒」这套流程，
就得引入真正的冲突合并或 CRDT——对个人投递台账这种低频低并发场景，不值得，
流程纪律就够了。

> **补充：外部写回走哪条路值得挑一下。** 面板本身需要一枚 token（它直接请求 `api.github.com`）；
> 但如果外部写回是**同一台机器上的 AI/脚本**，而本机已有该账号的 SSH 密钥，那么
> `git clone → 改 → push` 这条路**不需要额外 token**，权限面更小、也更好审计（每次写回都是提交）。
> 无论走哪条路，坑 3 的 `savedAt` 规则和坑 4 的「先拉最新」都适用。

## 坑 5：带 `break-inside: avoid` 的排版，砍内容不一定收得回页码

**现象**：简历溢出到第 3 页，而第 3 页上只站了 2 行。**连续两轮压缩内容**（累计砍掉约 300 个汉字）
之后，页数**还是 3**——第 3 页的内容从 681 字符降到 184 字符，就是不肯回到第 2 页。

**根因**：模板里区块带 `break-inside: avoid` / `break-after: avoid`，**整块不会被拆开分页**。
第 2 页此时只剩 25pt 可用，末尾那一块高 80pt，于是整块被推到第 3 页。
所以需要的不是"再砍一点内容"，而是**补足「该块高度 − 剩余空间」**
（本例 80 − 25 ≈ 55pt，约等于 3.5 行正文）。

**正解：先量缺口，再动手。** 别凭感觉反复压缩。量一下每页的剩余空间与页尾块高度：

```python
import pymupdf
d = pymupdf.open("out.pdf")
for i, p in enumerate(d):
    blocks = p.get_text("blocks")
    bottom = max(b[3] for b in blocks)
    print(f"p{i+1}: chars={len(p.get_text().strip()):5d}  末块底y={bottom:6.1f} / 页高 {p.rect.height:.0f}")
```

「页高 − 末块底 y − 下边距」就是剩余空间；和末块高度一比，缺口立刻显形。
本案例最终靠「删掉一条与目标岗位关联度最低的**整条项目** + 压缩一条不含数字的表述」补足 55pt，收回 2 页。

**附带教训：共用样式文件不要为单个版本调参。**
样式里那个行距变量（`--lh`）确实是页数的主要调节阀，模板注释甚至明说「溢出时优先调它」——
但它是**所有版本共用**的，调一下会连带改变**已经投出去的**那些版本的排版。
宁可改内容，也别偷偷改共用样式。

## 坑 6：面板类工具先查它有哪些状态值——没有「待投递」就别建记录

**现象**：想替用户把「还没投、但简历已经准备好」的岗位提前建进面板，好让它出现在待办里。
结果发现**没有可用的前置状态**。

**根因**：动手前没读源码。翻出状态枚举才发现它**从「已投递」开始**
（`已投递 / 测评 / 笔试 / AI面 / 一面 / 二面 / 三面 / HR面 / Offer / 已挂 / 已放弃`），
压根没有「待投递」这一档。而且旁边还有一条 **`STALE_DAYS = 15`：流程连续 15 天无进展，
自动标记为已挂**。

**后果**：硬建记录只能填「已投递」——**假数据**；搁置 15 天还会被自动标成「已挂」，
把真实投递记录的可信度一起污染。

**正解**：

- **未投递的岗位写在补充索引里**（`applications.yaml` 的 `stage`，它允许「待投递」），**不进面板**
- 面板只记录**真实发生过**的投递动作
- 通用做法：**这类工具的状态机与自动规则，动手前先读源码确认**——枚举值、自动挂起/降级规则、
  去重逻辑，往往都不写在说明文档里，而在源码里

> 这条坑的来源很典型：用户自己早就在操作说明里写了「还没投就建记录会触发误判」，
> 但**原因**（源码里那两个常量）是很久以后才被查出来的。写下「不要做什么」时，
> 最好同时写下**为什么**——否则下一个人、或下一次的 AI，还会再试一遍。

## 附：一句话总结

> `file://` 会丢数据 → 用 `https://` 稳定 origin；
> 预置/写回文件传原始 JSON（GitHub Contents API 自己套 base64，git 不套）；
> 外部写回时 `savedAt` 要比对端新；
> last-write-wins 下，外部改数据前先拉最新版、提醒应用暂停保存；
> 分页排版砍内容不一定有效——先量「页尾块高度 − 剩余空间」，再决定删多少，
> 且不要为单个版本改共用样式；
> 面板类工具的状态枚举与自动规则先读源码，没有的前置状态就用补充索引代替。
