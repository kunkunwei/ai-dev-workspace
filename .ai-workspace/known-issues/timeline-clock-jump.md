# 无保电 RTC 设备的时间线不能信墙钟，必须用单调时钟

## 现象

排查启动慢的问题时，几条时间线**互相矛盾**：

- 内核日志显示的时间早于上一次关机时间
- `journalctl` 的排序与事件的实际先后不符
- 容器记录的启动耗时与 `docker inspect` 对不上

而且同一个事件在三个来源里有三个时间。

## 根因

设备**没有保电 RTC**（掉电后时钟不保存）。一次开机过程中，墙钟会被设置多次：

1. 上电：内核用一个极早的时间起点（例如 1970 附近）
2. 内核 RTC 子系统接管：可能跳到另一个值
3. 读取上次关机时间：可能**落后**真实时间若干分钟
4. NTP 同步完成：**前跳**若干分钟

四次跳变意味着：**跨越跳变点的两条日志，时间戳差值与真实间隔无关**。

## 处置

**所有时序分析一律改用单调时钟**：

| 目的 | 用这个 | 不要用 |
|---|---|---|
| 查看内核事件顺序 | 裸 `dmesg`（相对时间） | `dmesg -T`（墙钟） |
| 查看 systemd 时序 | `journalctl -b -o short-monotonic` | 默认格式 |
| 计算启动耗时 | `/proc/uptime`、`systemd-analyze` | 日志时间戳相减 |
| 容器启动耗时 | 容器状态里的单调时间字段 | 容器内外墙钟对比 |

**判据**：如果你看到"后发生的事件时间戳更早"，直接判定时间线不可用，换单调时钟重测。

## 顺带发现

因为是按里程碑测量而不是按时间戳相减，反而量出了真实的启动依赖链：

```
内核 → 容器运行时 → 业务容器 → 网卡静态地址 → 设备绑定 → 数据源就绪
      → 时间基准 → 传感器出图 → 上层应用可用
```

链上**任何一环失败，下游会无限期停滞**（没有超时、没有重试）。
这个发现的价值高于原本要查的"启动慢"问题。

## 教训

- 不能用墙钟做时序分析，除非你确认设备的时钟是单调的
- "时间对不上"本身就是一个信号：可能不是日志错了，而是**时钟在跳**
- 排查启动问题时，先画出**依赖链**，再谈优化；否则优化的是无关环节
