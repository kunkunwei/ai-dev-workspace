# 冷启动时序测试规范

## 目的

回答两个问题，且必须是**可重复的**：

1. 「上电到可用」到底慢在哪一环？
2. 有没有**竞态**（两个组件的就绪顺序不固定）？

## 前提：一律用单调时钟

无保电 RTC 的设备，墙钟在一次开机内可能跳变 3~4 次
（详见 `known-issues/timeline-clock-jump.md`）。所以：

```bash
journalctl -b -o short-monotonic     # systemd 侧
dmesg                                 # 内核侧（不要用 -T）
cat /proc/uptime                      # 计算总耗时
```

## 里程碑定义

按**依赖顺序**排列，每个里程碑都要有一个**可观测的判据**（不是"应该起来了"）：

| # | 里程碑 | 判据 |
|---|---|---|
| 1 | 内核就绪 | 内核完成初始化 |
| 2 | 容器运行时就绪 | 可接受容器创建请求 |
| 3 | 业务容器全部起来 | 容器状态为运行中 |
| 4 | 网卡拿到静态地址 | 目标地址已配置 |
| 5 | 设备绑定成功 | 驱动完成绑定且无报错 |
| 6 | 数据源就绪 | 开始产生数据 |
| 7 | 时间基准就绪 | 时间源开始发布 |
| 8 | 传感器出图 | 图像话题有帧 |
| 9 | 上层应用可用 | 健康检查通过 |
| 10 | 外设就绪 | 音频/显示等外设枚举完成 |

**判据要能一条命令验证**，否则测出来的数字无法复核。

## 关键发现（示例）

真正的问题往往不是"某一环慢"，而是**环与环之间有竞态**：

> 网卡静态地址在启动后 40~46 秒才配好，而某个驱动在启动后 ~10 秒就尝试绑定到该地址。
> 绑定失败后驱动**只打日志不退出**，于是容器看起来"起来了"，实际永远起不来。

这类问题的特征：**现象偶发**，且与启动顺序相关。所以测试必须**重复多次**。

## 执行要求

- **连续至少 10 次**冷启动，记录每次的里程碑时间
- 每次之间**断电等待 ≥ 30 秒**（否则不算冷启动）
- 记录**最坏值**而不只是平均值——偶发问题只在最坏情况下暴露
- 结果落盘留档，作为后续改动的对照基线

## 输出格式

```
里程碑            目标     实测(10次)        结论
1 内核就绪        —        10.1~10.3 s       稳定
2 运行时就绪      ≤30 s    16.8~17.2 s       稳定
3 容器起来        ≤60 s    41.7 / 53.3 s     ⚠ 波动大
4 网卡地址        —        40~46 s           ⚠ 晚于 #5
5 设备绑定        —        ~10 s             ❌ 竞态：早于 #4
...
```

**标注符号约定**：✅ 达标 / ⚠ 波动或临界 / ❌ 竞态或失败。

## 竞态的处置原则

发现竞态后，不要靠"加大延时"解决——那只是降低触发概率。正确做法是**把顺序变成显式的等待**
（等某个可观测条件成立），并在超时后**明确失败**而不是静默继续。
