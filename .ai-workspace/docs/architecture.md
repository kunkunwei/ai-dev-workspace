# 架构说明

本文说明这套工作区为什么长成现在这样，以及几个被否决的替代方案。

## 1. 根本约束：模型没有跨会话记忆

所有设计都是从这一条推导出来的。

一个 AI 编码会话结束时，模型不保留任何状态。下一次会话开始时，它对项目的了解**只来自你这次给它的上下文**。由此产生三个连锁问题：

1. **它会补全缺失信息**。信息不全时，模型的默认行为是给出一个"看起来合理"的值，而不是承认不知道。这个值一旦写进代码或文档，就会一路传播下去。
2. **它会重复提问**。同样的问题在不同会话里被反复问，浪费的是人的时间。
3. **它会给出与事实矛盾的结论**。如果上下文里只有一半真相，推理再正确，结论也是错的。

**对策**：把"事实"从对话里搬出来，放进文件。

```
.ai-workspace/
├── facts/          事实源：环境、接口、配置（唯一可信来源）
├── tasks/          任务状态：在做、已做、卡在哪
├── known-issues/   已知问题：踩过的坑与根因
├── procedures/     流程：可复用的操作手册
├── decisions/      架构决策记录（ADR）
└── knowledge/      领域知识
```

配合一条硬规则：**缺失值必须显式标注 `UNKNOWN`，禁止猜测填充**。

这条规则看起来琐碎，但它是整套体系的地基——它把"模型的默认行为"从"编造"改成"承认不知道"，后者才是一个可被审计的起点。

## 2. 为什么不用 RAG / 向量库

这是最常见的一类替代方案，但我们明确否决了。理由不是技术上不可行，而是**它解决的不是这个问题**。

| 维度 | RAG / 向量检索 | 文件化事实源 |
|---|---|---|
| 解决的问题 | "内容太多，检索不过来" | "事实没有被记录下来" |
| 是否需要先有结构化内容 | 是（否则检索的也是垃圾） | 否（这是它的前置工作） |
| 可审计性 | 低（检索结果不可预测） | 高（哪一条事实来自哪个文件，路径明确） |
| 时效性 | 检索到过期内容时不自知 | 元数据带 `updated` 与 `status`，过期可见 |
| 增量成本 | 需要嵌入模型、向量库、索引维护 | 零（就是文件） |

**关键判断**：当文档总量在几百篇量级、且已经有索引和分层加载时，检索带来的收益低于它引入的不可预测性。真正稀缺的不是"检索能力"，而是**"这份事实到底是真是假、是什么时候写的、还有效吗"**——这需要结构，不需要向量。

我们保留了明确的反对意见记录在 ADR 里，并写明了触发重新评估的条件：**文档量级增长到索引无法有效导航时**再考虑。

## 3. 为什么要分层加载而不是全量注入

一个天真的做法是把所有文档都塞进系统提示。它在文档量小时能工作，然后会以两种方式失败：

1. **撞上上下文窗口**——文档继续增长，直到某个时刻直接装不进去。
2. **稀释注意力**——在真正需要的信息之前，模型要穿过大量无关内容。上下文越长，模型对其中任何一段的利用率越低。

所以改成三层：

```
第 1 层：检查点（约 4 KB）        ← 上次做到哪、下一步是什么
第 2 层：当前任务（按需）          ← 这次要动的那一件事
第 3 层：索引 → 目标文档（按需）    ← 需要细节时才加载
```

第 3 层的"索引"是关键：它带 `devices` 和 `stack` 两个维度，可以按平台或技术栈筛出相关条目，而不必遍历全部文档。

## 4. 为什么要有"任务退休"机制

任务文件如果不加约束，会单调增长：每完成一件事就追加一段。它最终会变成一份流水账——**体积大、信息密度低、没人读完**。

对策是给任务文件一个**硬上限（30,000 B）**和一个**唯一出口**：

```
任务完成
  → 整块正文追加到归档文件（按月）
  → 从任务文件里精确删除该块
  → 在已完成索引里追加一行
  → 跑校验，确认没有残留
```

这样任务文件永远只包含"正在做的事"，而历史仍然可查——只是被移到了按时间组织的归档里。

## 5. 为什么校验要"带预算"

校验器如果只回答"合规/不合规"，会有一个副作用：**规则越加越多，文件越长**。

所以 `ws-lint.cjs` 里凡是跟体量相关的检查，都带**阈值与分级**：

| 对象 | 告警 | 失败 |
|---|---|---|
| 规范入口注入成本 | 12 KB | 15 KB |
| 任务文件 | — | 30,000 B |
| 检查点 | — | 40 行 / 1200 中文字符 |
| 元数据覆盖率 | — | < 90% |

这意味着"规范本身膨胀"也会被拦住——**这是很多规范体系最终失效的原因**：为了修一个问题加一条规则，规则加起来比问题还大。

## 6. 凭据卫生的边界设计

校验器检查凭据卫生，但**只检查目录与文件名的忽略规则，从不读取凭据内容**。

理由是：一个用来防止泄露的工具，自己不该成为泄露面。如果校验器会读取凭据值（哪怕是用于比对），那么它的日志、报错信息、CI 输出都可能带上明文。

同理，`.gitignore` 的注释里也写明了一条经验：

> 不要用 `*credential*.md` 这类宽泛通配——它会把审计文档与交接文档一并忽略，导致**该留档的资料反而推不上云端**。

忽略规则的精度问题，在真实项目里是会伤人的。

## 7. 多 Agent 编排的两个要点

### 7.1 模型路由

不是所有任务都值得用最强的模型。分派原则：

- **复杂度高 / 需要裁决 / 影响面大** → 高算力模型
- **边界明确 / 机械性 / 输出量大** → 低成本模型

后者的价值常被低估：它不只是省钱，更重要的是**把长输出挡在决策路径之外**——让主代理看到的是结论，而不是几千行日志。

### 7.2 lane 并行与冲突规避

多个 lane（如前端 / 后端 / 平台）可以并行，但必须满足：

- 各 lane 的**修改范围不相交**
- 每个 lane 有明确的 `cwd` 与允许路径
- 冲突时**停下报告**，而不是自动合并

最后一条是刻意的：自动解决冲突在缺乏全局视图时，产生的"看起来能跑"的结果比冲突本身更危险。

## 8. 这套东西的适用边界

它**不是**通用最佳实践，而是针对一类具体场景的方案：

- ✅ 适合：长期演进的项目、多人（或多 Agent）协作、对"事实准确性"要求高、上下文成本敏感
- ❌ 不适合：一次性脚本、探索性原型、没有长期维护需求的仓库

在这些场景下，这套规范的开销大于收益。**判断标准是：你是否曾经因为"某个事实记错了"而付出过代价。** 如果没有，就先不要引入。
