# AI Dev Workspace

> 把「AI 辅助研发」从「会用工具」做成**有规范、有工具、有量化收益**的工程实践。

一套面向 AI 辅助研发（AI Coding / AI Agent 协作）的**文件化工作区规范 + 强制校验工具链**。

不是又一个 prompt 合集，而是把 AI 协作里反复出问题的地方固化成可执行的规则与检查：

- 模型**没有记忆** → 用文件化事实源替代对话记忆
- 模型**会声称完成** → 用独立验收代替信任
- 模型**不知道边界** → 用四级权限与委派协议约束
- 上下文**成本失控** → 用索引化与按需加载压缩
- 文档**会腐化** → 用机器生成索引与强制校验层兜住

---

## 一、它解决的具体问题

| # | 问题 | 典型现象 | 本仓库的方案 |
|---|---|---|---|
| 1 | **跨会话上下文丢失** | 新会话不知道昨天改了什么，模型开始"合理推测"出错误结论 | 文件化事实源 + 强制 `UNKNOWN` 标注（**禁止用猜测值填空**） |
| 2 | **模型输出不可验证** | AI 回"已完成"，实际没做或做错 | 独立验收原则 + 构建期断言 + 单变量 A/B 对照 |
| 3 | **操作边界不清** | AI 改到不该改的文件、执行未授权的命令 | 四级操作权限 + 委派协议（强制指定目录/范围/禁止项/验收标准） |
| 4 | **上下文成本失控** | 每个新会话都要重新加载几百 KB 文档 | 索引化 + 分层按需加载（**降约 95%**） |
| 5 | **文档腐化** | 索引过期、空占位文件、失效引用、凭据误入库 | 机器生成索引 + 带预算的强制校验层 |
| 6 | **长任务丢状态** | 长会话被压缩后，任务上下文断裂 | 检查点 + 任务退休归档 + 交接文档模式 |

|---|---|---|---|
| **新会话上下文加载量** | 316,236 B（≈98k tokens） | 14,238 B（≈4.4k tokens） | **↓ 约 95%** |
| 文档元数据覆盖率 | — | 100% | 索引可机器生成 |

## 五、四个核心设计

### 1. 文件化事实源，而不是依赖模型记忆

任何跨会话需要保留的事实，必须落到文件：事实源、任务状态、已知问题、流程、架构裁决。

**关键约束**：缺失值必须显式标注 `UNKNOWN` / `NEEDS_CONFIRMATION` / `TODO`，**禁止用"看起来合理"的值填充**。

理由很直接：模型在信息缺失时的默认行为是补全出一个合理的值，而这个值会一路传播下去，
最后变成一个谁也不知道是假的事实。

### 2. 独立验收，而不是信任模型的完成声明

规则原文（`core/engineering-rules.md`）：

> 不得仅依据执行方的完成声明判断成功；必须独立检查版本差异、约束符合性和用户要求。

配套三个手段：**构建期断言**（把"人记得检查"变成"机器强制检查"）、
**单变量 A/B 对照**（只改一个变量，配合可量化指标验证）、**证据归档**（可重放）。

### 3. 四级操作权限 + 委派协议

| 级别 | 含义 |
|---|---|
| `READ_ONLY` | 默认。只读分析、扫描、报告 |
| `BUILD` | 可在本地构建、跑测试 |
| `DEPLOY` | 可发布、可部署到目标环境 |
| `DANGEROUS` | 删除、迁移数据、改历史、重启系统等 —— **永远逐次人工确认** |

每次把任务交给执行方时，**必须显式给出**五件事：目标与验收标准、工作目录、
允许读写的路径范围、禁止事项、测试策略。缺任何一项都不算一个合格的委派。

### 4. 主代理 / 执行子代理的模型路由

不是所有任务都值得用最强的模型：

- **主代理**（高算力模型）：需求理解、方案裁决、跨模块决策、最终验收
- **执行子代理**（低成本模型）：边界明确的扫描、比对、机械检查、长输出压缩

收益是双重的：**省钱**，以及**避免长输出污染决策上下文**——让主代理始终只看到结论和关键证据，
而不是几千行日志。

## 六、强制校验层做了什么

`tools/ws-lint.cjs` 是这套规范的执行者。它把"规矩"变成"能不能提交"，覆盖 9 类检查：

| # | 检查 | 作用 |
|---|---|---|
| 1 | 规范入口注入成本预算 | 防止入口文件无限膨胀（**它是每次会话的固定成本**） |
| 2 | 任务文件体量上限 | 防止任务文件变成流水账 |
| 3 | 检查点行数 / 字数上限 | 强制检查点保持"30 秒读完" |
| 4 | front-matter 覆盖率 | 低于阈值直接失败（索引生成的前提） |
| 5 | 索引新鲜度 | 内容改了但索引没重生成 → 报错 |
| 6 | 空占位文件 | 防止"占个位置回头再写"永久残留 |
| 7 | **凭据卫生** | 检查 `.gitignore` 是否覆盖凭据目录；**只查路径模式，不读值** |
| 8 | 失效运行时引用 | 防止文档引用已不存在的工具 / 模型标识 |
| 9 | 规则可达性 | 防止出现"写了但没人读得到"的规则文件与多个矛盾入口 |

**第 3 与第 1 条的设计值得一提**：它们带**阈值与分级**（告警 / 失败），而不是简单的"合规/不合规"。
这意味着"规范本身膨胀"也会被拦住——**这是很多规范体系最终失效的原因**：为了修一个问题加一条规则，
规则加起来比问题还大。

**第 7 条**：校验器只检查"凭据目录是否被忽略"，**从不读取凭据内容**。
一个用来防止泄露的工具，自己不该成为泄露面。

## 七、怎么用到自己的项目

这套东西是通用方法论，不绑定任何具体技术栈。迁移方式：

1. 把 `AGENTS.md` 改成你自己项目的规范入口（保留结构，替换内容）
2. 保留 `.ai-workspace/core/` 的规则骨架，按你的风险等级调整权限分级与禁止项
3. `tools/*.cjs` 可直接拷走用（只有 Node 内置依赖）：
   ```bash
   node .ai-workspace/tools/ws-fm-backfill.cjs  # 给存量文档补元数据
   node .ai-workspace/tools/ws-index.cjs        # 生成索引
   node .ai-workspace/tools/ws-lint.cjs         # 强制校验
   ```
4. 从 `ws-lint.cjs` 里删掉你不需要的检查项，**保留索引新鲜度与凭据卫生这两条**

## 八、使用边界（写在前面）

- 本仓库是**方法论与工具层的参考实现**，已做脱敏处理。原项目中的公司标识、产品代号、
  设备信息与本地路径全部替换为占位符；`known-issues/` 与 `procedures/` 下的文档是
  **通用化后的工程经验**，用于演示元数据与索引机制。
- `tools/` 按本工作区的目录约定编写；如果你把目录删空再运行，会看到"不可达 / 索引缺失"
  之类的检查失败 —— 这是**预期行为**，它本来就是个检查器。
- 规范不是教条。它的价值在于把"每次都靠人记住"变成"机器每次都检查"；
  具体阈值（预算、上限、覆盖率）应该按你的团队规模调整。

## 九、一句话总结

> AI 辅助研发的瓶颈往往不在模型能力，而在**工程纪律**：
> 事实落在哪、谁来验收、边界划在哪、成本怎么控。
> 这份仓库就是把这四件事变成文件、脚本和检查。
